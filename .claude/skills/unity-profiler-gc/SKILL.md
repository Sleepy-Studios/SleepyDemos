# GC 分配定位与修复

已有报告先读 summary 与主要 GC 热点，不重复解析。需要录制、加载或异常帧时读取 [unity-performance](../unity-performance/SKILL.md)，沿同一实例的 sd_profiler_ 操作。

## 定位

1. 区分常态每帧、周期事件、用户操作、一次性加载。AllocEvents 是分配事件数，不是业务调用次数；分配字节不证明峰刺来自回收。
2. 先按字节量、频率和场景相关性选候选，再读 samplePath、实际 callstack 和当前源码。Core.Runtime、Hotfix 和具体 Demo 归属按符号识别，不写死程序集名单。
3. 分离 Editor、Test Runner、资源模拟、Shader/Inspector、采样工具自身的分配。引擎下层分配虽在业务调用链中，也不能当作业务方法直接 new。
4. 调用链不足时，只补相关帧/路径的诊断，不用大规模 Deep Profile 干扰正式基线，不靠二进制字符串或源码 new 数量估算实际分配。

## 优化

- 先检索调用方和公共实现，选择等价循环、已有缓存、变化时刷新及局部复用；检查集合容量、失效、重入、异步持有、隐藏/销毁和失败路径。
- 不机械替换 foreach、所有字符串或 Unity 对象字典；只有采样与实际类型确认分配或开销才修改。
- 不改变输入精度、玩法时序、动画、音频、UI 刷新可见时机，不为清零增加跨模块缓存、通用池或并行状态。
- 用户指定零 GC 时，明确常态热路径和一次性创建的口径；引擎与必要分配单列，不把统计过滤伪装成清零。

## 复测

旧报告重复解析不能证明收益。以包含新代码、同一场景/路径/设置的新采样确认字节量和频率下降，并验证生命周期与行为。默认复用既有检查，不新增永久测试；不主动检查 Hot Reload 补丁。

交付根因、修改、前后数字、残留原因和证据链接。实际验证过的项目经验按需要补充 [优化记录](references/verified-patterns.md)，不能将理论收益写成已验证。
