# Core / Hotfix 边界

## 目标

这份文档只解决一个问题：
什么该放 Core，什么该放 Hotfix。

## Core 负责什么

Core 负责“业务发生之前就必须存在”的能力：
- 启动状态机
- 资源服务抽象、初始化与下载
- 程序集装配
- 公共 UI 框架
- 通用服务、组件、工具类
- 编辑器构建与辅助工具

Core 的关键词是：
- 通用
- 稳定
- 可复用
- 被业务依赖

## Hotfix 负责什么

Hotfix 负责“业务接管之后”的能力：
- 业务入口
- 主菜单
- Demo 玩法模块
- 页面和交互逻辑
- 和具体业务规则强绑定的流程

Hotfix 的关键词是：
- 业务
- 页面
- 流程
- 玩法

## 常见判断题

### 情况 1
“我要加一个新的资源检查和下载步骤。”

结论：放 `Core.Runtime`

### 情况 6
“我要替换或扩展资源底层实现。”

结论：优先扩展 `Core.Runtime` 的 `IResourceService` / `IResourceLoader` 实现和注册点，不要让 Hotfix 或 UI 层直接依赖具体资源框架。

### 情况 2
“我要让主菜单多一个按钮，点进去进入新的 Demo。”

结论：主菜单逻辑放 `Hotfix`，Demo 资源放 `Assets/LoadResources/Demos/<DemoId>/`

### 情况 3
“我要做一个所有页面都会复用的 View 基类。”

结论：放 `Core.Runtime`

### 情况 4
“我要做一个只有某个 Demo 会用到的倒计时规则。”

结论：放 `Hotfix`

### 情况 5
“我要加一个 Unity 菜单命令，用于构建热更包或同步配置。”

结论：放 `Core.Editor`

## 禁止事项

- 不要把某个具体玩法硬塞进 Core
- 不要让 Core.Runtime 反向依赖 Hotfix
- 不要因为当前方便，就把临时业务判断埋进启动链路

## 文档维护要求

只要出现以下变化，必须同步更新本文档：
- Core 新增了新的公共子系统
- Hotfix 新增了新的业务入口模式
- 原有边界被重新划分
- 某类能力从 Hotfix 上提到 Core，或反过来下沉
