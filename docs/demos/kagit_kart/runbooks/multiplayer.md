# 创建与加入玩家 Host 房间

## 适用场景

纸艺卡丁车通过一名玩家创建Host，其他玩家按IP或域名加入同一个房间。Host同时参赛并执行服务器规则，使用FishNet/Tugboat真实UDP，默认端口为 `7777`。当前支持单场比赛与四章大奖赛，房间容量2/4/8人，至少两名真人；剩余席位由AI补齐八车网格。计时赛仍使用单人入口。

## 前置条件

- 双方使用兼容的协议、内容版本与资源。当前只有纸艺卡丁车接入[公共网络会话](../../../modules/network-session.md)，没有账号登录、公共房间目录、随机房间码、Relay或自动NAT穿透。
- 同一局域网内，来宾使用Host机器的可达IPv4/域名；房间“复制地址”提供本机网络地址。`127.0.0.1` 只用于同一机器上的两个独立进程，不代表另一台机器能够连接。
- Host所在系统允许游戏通过防火墙接收UDP `7777`，该端口没有被其他Host占用。同一机器上同时运行多个创建房间实例会争用默认端口。
- 跨公网连接时，需要Host具有可达公网地址，并把路由器UDP `7777` 映射到Host机器。复制的局域网地址不能直接给公网来宾使用；运营商NAT或双重NAT下仅设置本机防火墙通常不足以建立入站连接。当前程序不代办公网地址发现或路由配置。

## 创建、加入与开始

1. 从正式 `AppEntrance` 进入Hub的“纸艺卡丁车”，在封面开始后选择联机。
2. 房主选择创建房间，填写房间名，选择2/4/8人、80g/120g/200g及单场或大奖赛。单场可以选择四条赛道；大奖赛从雏菊草原开始。创建成功后进入房间，Host本身占一位真人。
3. 来宾选择加入房间，输入显示名、Host地址和端口。可以分别填写 `192.168.1.20` 与 `7777`，也可以粘贴房间复制的 `192.168.1.20:7777`。显示名用于展示，实际成员身份由连接分配。
4. 在大厅选择未被占用的角色，各玩家点击准备。成员行依据公共会话的 `AuthorityMemberId` 显示“房主”或“车手”，不按显示名或列表位置猜测。房主可在大厅修改房间设置；修改设置重置全员准备，更换角色重置该玩家准备，容量不能低于当前连接人数。
5. 至少两名真人且所有连接玩家已准备后，房主开始比赛。各端先加载/激活比赛资源，房间显示加载状态，全部玩家资源准备完成后才统一进入倒计时。玩家不需要手工发送加载完成通知。
6. 正常驾驶与道具输入沿键鼠、手柄、触屏的公共输入链。联机暂停只暂停本机操作/页面并提交中性输入，服务器比赛与其他玩家继续。

只有大厅接受新连接。满员、准备中、比赛中、赛后Results阶段以及协议/内容不匹配均明确拒绝，不会伪装成功或回退单人模式。

## 结算、下一场与退出

单场结束后，玩家从结算返回原房间，再次准备，由房主开始下一场。房主回到大厅后可以修改单场设置并重新接纳玩家；不能在进行中的比赛单独重赛。

大奖赛顺序为雏菊草原、博斯普鲁斯夜景、冰川通道、书写桌面。每章先显示本场成绩与总积分榜，下一章先回原房间重新准备，由Host推进章节并按积分倒序排网格。杯赛未完成时房间保持赛后状态，不能加入新成员、改角色或选赛；四章完成后可展示颁奖，房主重新开放大厅，再开杯赛从草原与新积分开始。

准备阶段60秒未全员加载完成，或者连接真人不足两名，房间回到大厅并提示原因，旧轮次准备任务取消。修复各端资源/连接后重新准备，不会让仍在加载的旧任务恢复上一轮比赛。大奖赛后续章节准备超时后重试，保留当前章节与上一章已结算积分，并重新使用积分逆序网格；不再因章节已进入准备状态而退回默认角色顺序。

普通玩家比赛中离开或断线，Host让其赛车由AI接管；大厅/结果阶段清理断线成员名额。没有正在比赛的重连或观战入口。Host退出或失联会结束整个房间，来宾收到断线提示并返回联机入口；本版没有Host迁移。退出会等待底层连接和载体释放，完成后允许重新创建/加入。

## 网络行为与现实限制

联机以120Hz权威固定步推进，约30Hz发送完整共享比赛快照。客户端使用官方FishNet Replicate/Reconcile预测与校正自己的赛车，远端赛车和道具由共享快照呈现；名次、道具作用和积分以Host为准。Host只推进一份权威模拟。详细职责与完整状态边界见[模块说明](../module.md#联机房间与状态同步)。

准备/开始与最终赛果采用可靠快照，普通比赛共享快照请求不可靠发送。但当前八车完整状态通常4～8KiB，超过MTU后FishNet会自动转为可靠分片并重组；丢片仍可能造成重传和队头等待。拥有者校正约400B，通常可以低于MTU。不能把“大包请求不可靠”等同于“所有状态都可以独立丢帧”，弱网驾驶与结果交付需要实际验收。

## 排障

| 现象 | 核对顺序 |
|---|---|
| 创建失败 | 默认UDP端口是否已被另一Host占用，Console/页面是否有资源或协议错误。 |
| 加入超时 | Host是否仍在大厅；地址与端口是否正确；使用本机地址还是对端地址；防火墙、LAN隔离、公网映射与NAT可达性。公共连接等待上限15秒。 |
| 人数已满或比赛已开始 | 等房主开放大厅；准备/比赛/赛后阶段不能靠空席加入。 |
| 开始按钮不可用 | 至少两名连接真人，全员Ready；房主修改设置或玩家改角色后需要重新准备。 |
| 准备超时 | 查看两端资源加载异常和加载状态；回大厅后重新准备。不要只让Host跳过加载等待。 |
| 本机无油门、其他车仍前进 | 检查本机暂停、失焦或后台门闩，恢复焦点并明确继续；联机暂停不会冻结Host。 |
| 弱网姿态滞后、突跳 | 分开记录客户端实际RTT、丢包条件、拥有者校正与大共享快照等待；不能用增加延迟掩盖状态缺失。 |

每组保留11个约一秒间隔样本。原生 `NetPeer.RoundTripTime` 是SDK滚动统计，包含基础链路与丢失后的Ping等待，阶段切换初期还包含上一组样本；`NetPeer.Ping` 为其一半。表中范围不是固定延迟或驾驶响应保证。Host原生统计明确选择远端Peer，排除本机loopback。

本轮FishNet `TimeManager.RoundTripTime` 持续为0。120Hz下Editor经常一帧补多个tick，SDK `NetworkConnection.CanPingPong()` 在最近1秒有多tick时拒绝回Pong；报告记录的 `recentMultiTicks` 为true。零值表示该统计未更新，不能解释为0ms往返，也不能用配置目标100/200ms替代实测。本地错误预测在一次现成校正到来后约0.014秒恢复，只证明当次校正发生，不能作为完整RTT或弱网下固定修正耗时的承诺。

Editor默认验证仍遵循[项目测试架构](../../../architecture/testing.md)及[正式测试流程](../../../runbooks/run-unity-tests.md)。EditorSimulate会复用编辑器已加载Hotfix程序集；独立Player必须使用本轮最新产物，旧首包、同进程Host或双Editor通过都不能证明IL2CPP、裁剪与原生发布通过。构建与模式边界见[热更新模块](../../../modules/hotfix.md)。一次性双端/弱网探针和角色配置验收结束后清理，实测报告作为证据保存，不把临时测试文件列为长期产品入口。
